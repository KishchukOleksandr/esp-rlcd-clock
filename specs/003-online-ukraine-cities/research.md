# Phase 0 Research: Розширений онлайн-вибір будь-якого міста України

**Feature**: `003-online-ukraine-cities`  
**Date**: 2026-11-25  
**Target Hardware**: Waveshare ESP32-C6-DEV-KIT-N8 (RISC-V @ 160 MHz, 512KB SRAM, 8MB Flash, ESP-IDF v6.1)

---

## 1. Вибір зовнішнього сервісу геокодування населених пунктів України

- **Decision**: Використати **Open-Meteo Geocoding API** (`https://geocoding-api.open-meteo.com/v1/search`) із параметрами `name=<url_encoded>&countryCode=UA&language=uk&count=10`.
- **Rationale**:
  - Повністю публічний API без обов'язкової реєстрації або введення API-ключа кінцевим користувачем (відповідає припущенням специфікації).
  - Побудований на базі GeoNames: охоплює всі міста, селища та села України і автоматично ранжує результати за населенням/релевантністю (`FR-001`).
  - Підтримує нативну фільтрацію `countryCode=UA` (ISO-3166-1 alpha-2) і повертає поле `country_code` у кожному елементі для додаткової захисної перевірки на стороні ESP32 (`FR-003`, `SC-003`).
  - Підтримує `language=uk` — повертає україномовні назви населених пунктів (`name`), областей (`admin1`) та районів (`admin2`), коректно шукає кирилицею (`і`, `ї`, `є`, `ґ`, апострофи, дефіси, пробіли) та латиницею (`FR-004`, `FR-009`).
  - Компактна JSON-відповідь: для `count=10` розмір тіла відповіді становить орієнтовно 2.5–5 КБ, що легко вміщується у статичний буфер `12 КБ` без фрагментації купи на 512KB SRAM (`Constitution Principle III`).
  - Природно інтегрується з подальшим прогнозом погоди Open-Meteo для годинника (спільний кореневий пакет сертифікатів `esp_crt_bundle`).
- **Alternatives considered**:
  - *Nominatim (OpenStreetMap)*: жорстке обмеження 1 запит/сек, суворі вимоги політики використання (`User-Agent`), значно більші JSON-відповіді (20–40 КБ), повільніша відповідь та менш однорідна структура полів області/району.
  - *GeoNames Web Services*: потребує реєстрації облікового запису та передачі `username` у кожному запиті, що неприйнятно для відкритої прошивки без користувацьких ключів.
  - *Вбудована повна база ~29 000 населених пунктів України у Flash*: суперечить вимозі онлайн-вибору при підключенні до Інтернету, значно ускладнює підтримку перейменувань (декомунізація/деколонізація) та витрачає значний обсяг Flash і процесорного часу на пошук.

## 2. Механізм фактичної перевірки доступності Інтернету на ESP32-C6

- **Decision**: Виконувати неблокуючу перевірку фактичної доступності Інтернету через окрему легку FreeRTOS-задачу (`geo_probe_task`) у компоненті `geo_search` шляхом DNS-резолюції та TCP-підключення до цільового хоста `geocoding-api.open-meteo.com:443` із обмеженим таймаутом (`2500 мс`).
- **Rationale**:
  - На відміну від перевірки лише стану `WIFI_FSM_CONNECTED_STA`, TCP-підключення до зовнішнього хоста надійно відрізняє ситуацію «роутер без Інтернету» від реального виходу в Інтернет (`FR-002`, Уточнення Q4).
  - TCP-перевірка на порт 443 не виконує повного TLS-рукостискання, тому витрачає мінімум SRAM (< 2 КБ) і завершується за 50–300 мс, не витрачаючи ліміти HTTP API.
  - Перевіряє доступність саме того сервісу, який потрібен для онлайн-пошуку міст.
  - Запуск перевірки відбувається асинхронно за подією `STA_GOT_IP` (через `xTaskNotify`), а при `STA_DISCONNECTED` або фабричному скиданні статус миттєво скидається в `false` без блокування обробників подій Wi-Fi (`Constitution Principle II`).
  - Якщо пристрій підключений до Wi-Fi (`CONNECTED_STA`), але Інтернет був недоступний (`internet_available == false`), задача виконує періодичну повторну перевірку кожні `30 секунд`, щоб автоматично виявити відновлення Інтернету на роутері.
  - Додатково статус оновлюється за результатами реального пошукового запиту: успішна відповідь встановлює `internet_available = true`, а помилка DNS/підключення — `false` (із плановою повторною перевіркою).
- **Alternatives considered**:
  - *ICMP Ping (`esp_ping`)*: часто блокується корпоративними/домашніми фаєрволами та деякими провайдерами, а також не гарантує працездатність DNS/TCP:443.
  - *Повний HTTPS GET під час кожної перевірки*: витрачає ~40 КБ SRAM на mbedTLS handshake і зайвий трафік при кожному перепідключенні.
  - *Пасивна перевірка лише за `STA_GOT_IP`*: не відповідає уточненій вимозі `FR-002` (не виявляє «роутер без Інтернету» до моменту пошуку).

## 3. Управління пам'яттю, TLS та конкурентним доступом на 512KB SRAM

- **Decision**:
  - Використати стандартний `esp_http_client` із вбудованим пакетом сертифікатів ESP-IDF (`CONFIG_MBEDTLS_CERTIFICATE_BUNDLE=y`, `crt_bundle_attach = esp_crt_bundle_attach`).
  - Захистити виконання онлайн-пошуку одним FreeRTOS-м'ютексом (`s_search_mutex` із `xSemaphoreTake(..., 0)`), щоб одночасно виконувався максимум **1** зовнішній HTTPS-запит. Повторні одночасні запити негайно отримують `ESP_ERR_INVALID_STATE` → `HTTP 429 Too Many Requests` (`FR-011`).
  - Використовувати статичний буфер відповіді фіксованого розміру `12288 байтів` (`12 КБ`), доступ до якого можливий лише під `s_search_mutex` (нульова фрагментація купи для HTTP-тіла).
  - Виділити достатній стек для HTTP-сервера (`httpd_config.stack_size = 8192`) або виконувати `esp_http_client` у виділеній задачі з фіксованим стеком `8192` байтів для безпечної роботи mbedTLS із моніторингом `uxTaskGetStackHighWaterMark` (`Constitution Principle III`). Виконання в `httpd` із `stack_size = 8192` є простішим за умови 1 активного пошуку, але для гарантованого неблокування інших HTTP-маршрутів (наприклад, `GET /api/status`) під час 5-секундного пошуку краще збільшити `httpd_config.stack_size = 8192` і обмежити таймаут `esp_http_client` до `4500 мс` (сумарно `< 5000 мс` згідно з `SC-002`), водночас не блокуючи головний цикл і Wi-Fi FSM (`app_main`, `wifi_manager`, TWDT).
- **Rationale**:
  - На ESP32-C6 із 512KB SRAM один TLS-сеанс споживає ~35–45 КБ динамічної пам'яті на час з'єднання; два паралельні TLS-сеанси могли б призвести до вичерпання вільної купи. М'ютекс із миттєвою відмовою (`timeout = 0`) гарантує детерміноване пікове споживання пам'яті та повністю відповідає `FR-011`.
  - Статичний 12 КБ буфер у BSS виключає ризик фрагментації купи під час багаторазових пошукових запитів.
  - `CONFIG_ESP_TASK_WDT_TIMEOUT_S=10` безпечно перекриває максимальний таймаут пошуку `4.5 с`, і `esp_http_client` використовує неблокуючі сокет-очікування (`select`/`poll`), тому Idle-задача та інші FreeRTOS-задачі не голодують.
- **Alternatives considered**:
  - *Незашифрований HTTP (порт 80)*: Open-Meteo підтримує HTTPS як основний захищений транспорт; HTTPS із `esp_crt_bundle` запобігає підміні відповідей у локальній/публічній мережі та відповідає сучасним практикам безпеки.
  - *Динамічне виділення буфера під розмір `Content-Length`*: вразливе до надвеликих або chunked відповідей і спричиняє фрагментацію купи.

## 4. Обробка UTF-8, кирилиці та обмеження 64 байти для назви

- **Decision**:
  - Реалізувати чисті C-функції у `geo_search`:
    - `geo_search_utf8_char_count(const char *str)` — підрахунок кількості UTF-8 символів (кодових точок), щоб перевіряти мінімум 2 символи (`FR-011`), а не 2 байти (одна кирилична літера займає 2 байти UTF-8!).
    - `geo_search_url_encode()` — RFC 3986 percent-encoding байтів UTF-8 (коректно кодує кирилицю `і`, `ї`, `є`, `ґ`, пробіли `%20`, апостроф `%27`, дефіс `-` залишається без змін).
    - `geo_search_utf8_truncate()` — безпечне обрізання рядка до `<= 64` байтів строго по межі UTF-8 символу (не розриваючи багатобайтові послідовності `10xxxxxx`), якщо назва населеного пункту з зовнішнього API перевищує `LOC_NAME_MAX_LEN` (`64` байти).
- **Rationale**:
  - Пряма перевірка `strlen(q) >= 2` помилково пропустила б 1 кириличну літеру (2 байти). Підрахунок кодових точок UTF-8 усуває цей дефект.
  - Обрізання по межі UTF-8 символу гарантує, що будь-який результат із зовнішнього API пройде сувору валідацію `config_store_validate_location()` (`1..64` байти UTF-8) без пошкодження кодування (`FR-010`, Edge Cases).
- **Alternatives considered**:
  - *Перекласти кодування/фільтрацію тільки на браузер*: порушує вимогу безпеки (`Constitution Principle IV`) — сервер ESP32 зобов'язаний самостійно валідувати та санітизувати вхідні запити й зовнішні відповіді.
